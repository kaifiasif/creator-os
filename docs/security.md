# Security

Creator OS has accounts: each creator signs up with an email and password, and sees only their own archive, sources, drafts and results. Everything lives in one SQLite file. This page lists each common web-app risk, what the app does about it, and where the code is. Items that do not apply say why.

| Risk | Status | How |
|---|---|---|
| Cross-site scripting (XSS) | Protected | React escapes all text. The only raw-HTML spot is shadcn's chart style tag, built from static config. A Content-Security-Policy allows scripts from the app's own origin only, with no inline scripts (`src/http/middleware/security-headers.ts`), so an injected script cannot run. The session cookie is HttpOnly, so even a script that did run could not read it. |
| Cross-site request forgery (CSRF) | Protected | Two layers. The session cookie is `SameSite=Lax`, so browsers leave it off cross-site form posts. And every write, log-in and sign-up included, is refused when its `Origin` or `Sec-Fetch-Site` shows another site (`src/http/middleware/same-origin.ts`). |
| Sessions | Protected | A session is 32 random bytes in an `HttpOnly`, `SameSite=Lax` cookie, `Secure` with the `__Host-` prefix in production. The database stores only its SHA-256, so a copy of the database cannot be used to log in. Sessions last 30 days, a new one is issued at every log-in, log-out deletes it, changing the password or turning 2-step codes on or off ends every other session, and expired sessions are swept hourly (`src/modules/auth/`). |
| File upload validation | Protected | Extension allowlist, size limits (200 MB audio, 100 KB text), and a content check: audio must start with its format's signature, text must be valid UTF-8 with no NUL bytes (`src/modules/sources/intake.ts`). Files are stored under a generated id, never the uploaded name, and are never served back. |
| Broken object-level authorisation (BOLA/IDOR) | Protected | Enforced in the data layer, not the routes. Every repository is built for one signed-in creator (`createRepositories(db, userId)`), and every query filters by that owner: root tables carry `user_id`, and child rows (claims, drafts, decisions, agent runs, rehearsals) are reached only through a parent the creator owns. Someone else's id reads as 404, never 403, so ids cannot be probed. Composite foreign keys make the database itself refuse a run on another creator's source or a label on another creator's archive piece (`src/db/migrations/0003_accounts.sql`). `test/accounts.test.ts` tries every read and write against a second account. |
| Rate limiting | Protected | Per visitor: 600 API calls a minute, 60 costly calls (uploads, drafting, agents, rehearsal) per 10 minutes, counted per account (`src/http/middleware/rate-limit.ts`). Log-in: 10 wrong passwords or codes per 15 minutes per visitor, and 50 per email, so neither one machine guessing many accounts nor many machines guessing one account gets far, while a stranger cannot cheaply lock someone out. Attempts are counted before they run, so a burst of parallel guesses cannot slip past the cap. Behind a proxy the visitor is the last `X-Forwarded-For` entry, the one the proxy added, not the first, which a client can forge. Sign-up: 5 accounts per visitor per hour. Set `TRUST_PROXY=1` behind Render or Fly. Audience rehearsal also has spend caps: 10 rehearsals per draft per day and 25 interview questions per rehearsal. |
| JWT secrets | Not applicable | No JWTs are issued. Sessions are opaque random tokens checked against the database, so they can be revoked at once. |
| API keys kept server side | Protected | Claude, Groq, OpenAI and AssemblyAI keys are read from environment variables by the server only; the one model key the agents use (Claude's, or else `LLM_API_KEY`) is passed on to the agents service and nothing else. A model base URL must be https (or http on localhost). The web bundle contains no keys; `/api/config` reports which providers are on, never their keys. Keys go in headers, never URLs. |
| Password hashing | Protected | scrypt (N=2^15, r=8, p=3, per OWASP) with a random salt per password, compared in constant time (`src/modules/auth/passwords.ts`). Parameters are stored with each hash so they can be raised later. Passwords are 10 to 200 characters. An unknown email still runs a full hash check, and gets the same message as a wrong password, so log-in does not reveal who has an account. |
| Multi-factor authentication | Optional, per account | Settings, 2-step codes: standard TOTP (RFC 6238) that works with any authenticator app. Turning it on needs a code from the app; turning it off needs the password and a code. Each code works once, so a code seen over someone's shoulder cannot be replayed (`src/modules/auth/totp.ts`). |
| Permissions enforced server side | Protected | The client hides nothing that matters: blinding rules (hidden checks and agent predictions before a decision), consent for calls, the publish re-check and the results lock are all enforced in services, not the UI. |
| Row-level security (RLS) | Equivalent in the data layer | SQLite has no RLS. Its job is done by the owner-bound repositories above (the only code that runs SQL) plus the composite foreign keys. If the app moves to Postgres, enable RLS on the same `user_id` columns (see `docs/adr/001-sqlite-as-the-store.md`). |
| Webhook signature verification | Not applicable | The app receives no webhooks. AssemblyAI is polled, not called back. |
| Internal agents service | Protected | The Python agents listen on 127.0.0.1 only and need a random token generated at each start. Their callbacks to the app need a second token that works for one creator's draft and ends with that run, so the agents service cannot read anyone else's data. Both refuse to listen anywhere but loopback. The web app checks everything the service sends back (output shape, trace size and length) before storing it, because traces are shown to the creator and model text in them can be steered by a transcript. Tool failures reach the model as a generic message, with the detail kept in the server log. The child process gets only the environment it needs (no database path, no other keys) and logs with the same redaction rules (`src/modules/agents/agent-service.ts`, `tool-bridge.ts`, `agents/creator_agents/server.py`). |
| Server-side request forgery (SSRF) | Protected | The server only calls fixed provider hosts set by environment variables. The posted X link is validated and stored, never fetched. |
| Source maps | Off | `build.sourcemap: false` in `web/vite.config.ts`. |
| Default credentials | None | There is no built-in account or password. The first person to sign up creates the first account and takes over any data from before accounts. On a public server set `CREATOR_OS_OWNER_EMAIL` to your email: then only you can take that data over, and a stranger who signs up first gets an empty account. Set `CREATOR_OS_SIGNUP=closed` if nobody else should join. |
| Sensitive data in logs | Protected | Logs carry ids, counts and timings, never transcripts or drafts. Fields named like `authorization`, `token`, `api_key`, `secret` or `password` are redacted (`src/core/logger.ts`). 500 errors return a request id, not the stack. |
| Caller-supplied request ids | Protected | Only plain tokens are echoed back, so a header cannot inject text into responses or logs. |
| Account enumeration | Limited | Log-in never says whether an email exists. Sign-up has to say an email is taken; that answer is rate limited. |
| Security headers | On | CSP, HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, strict referrer policy, and a permissions policy that allows only the microphone. |
| Vulnerable dependencies | Clean | `npm audit` reports 0 vulnerabilities for the server and the web app (checked 2026-10-08). Run it again before each deploy. |

Known limits:

- There is no password reset by email, because the app sends no email. A creator who forgets their password needs the server owner to help. Turn on 2-step codes and keep the password in a password manager.
- 2-step secrets are stored as-is in the database, like the password hashes beside them. Whoever can read the database file can read them, so keep the file private and back it up encrypted.
- Rate limits are kept in memory, which suits the single process this app runs as. A second instance would need a shared store.
